# Field Manager: правила проєкту

Цей файл автоматично читає Claude Code на початку кожної сесії. Правила обов'язкові.

> ## ⛔ КРИТИЧНЕ ПРАВИЛО: жодних комітів до моєї перевірки
>
> **Заборонено виконувати `git commit` (і будь-які дії, що створюють коміт: `--amend`, `merge`, `cherry-pick`, `revert`, `stash pop` з комітом тощо), доки я особисто не переглянув зміни і прямо не написав, що можна комітити.**
>
> - Виконати підпункт, перевірити його і **зупинитися**. У відповіді вивести: список змінених файлів, короткий підсумок і запропоноване повідомлення коміту.
> - Мовчання, схвалення плану, слова на кшталт «продовжуй», «далі», «ок» щодо наступного підпункту **не є** дозволом на коміт. Дозвіл це лише явна фраза про коміт («коміть», «можна комітити»).
> - Не переходити до наступного підпункту, доки я не підтвердив поточний. Не накопичувати зміни кількох підпунктів у робочій директорії, якщо я явно не попросив об'єднати їх.
> - Якщо сумніваєшся, чи є дозвіл, його немає: питай.
> - Так само заборонено `git push`, `git reset --hard`, `git checkout -- .`, `git clean` та інші дії, що знищують або публікують роботу.

### Контекст

Тестове завдання на позицію Frontend Engineer. Веб-застосунок для управління сільськогосподарськими полями: інтерактивна карта з полями (GeoJSON), моніторингові точки з координатами WGS84 і MGRS, панель зі списком, фільтрами, пошуком і сортуванням. Без бекенду, лише mock-дані. Оцінюються якість коду, TypeScript без `any`, чиста архітектура, UX.

### Стек

- Vite, TypeScript strict, **npm** (файл `package-lock.json` комітимо)
- **React: остання мажорна версія, яку ставить шаблон Vite `react-ts`.** Не понижувати і не фіксувати версію вручну.
- **react-leaflet: мажорна версія, що підтримує встановлений мажор React.** Перед встановленням перевірити `peerDependencies` (наприклад, `npm view react-leaflet peerDependencies`). Якщо остання версія react-leaflet не підтримує цей мажор React, зупинитися і запитати мене. Не використовувати `--force` і `--legacy-peer-deps`.
- Leaflet
- Tailwind CSS
- **shadcn/ui** (CLI `npx shadcn@latest`). Згенеровані компоненти лежать у `src/shared/components/ui`, утиліта `cn` у `src/shared/lib/utils.ts` (реекспорт із пакета `cn`, заміни `clsx` + `tailwind-merge`).
- Zustand (по стору на фічу)
- `mgrs` (конвертація WGS84 → MGRS на фронтенді), `@turf/boolean-point-in-polygon`
- **ESLint + Prettier** (з `prettier-plugin-tailwindcss`)

### Скрипти (`package.json`)

### Правила залежностей (архітектурна домовленість, без автоматичної перевірки лінтером)

- Напрямок: `app → features → shared`. `shared` не імпортує з `features` і `app`.
- Фіча імпортує іншу фічу **лише через її `index.ts`**. Єдиний дозволений зв'язок: `points → fields`. `map` не знає про `fields` і `points`. `fields` не знає про `points`.
- Композицією фіч займається `app/`.
- `index.ts` фічі експортує лише публічне: головний компонент, компоненти карти, потрібні хуки, типи. Стор назовні не експортуємо.
- Ці правила перевіряються на code review, лінтером не форсуються: 3 фічі й один дозволений зв'язок видно одразу. На більшому проєкті форсувати через `eslint-plugin-boundaries` чи `no-restricted-imports`.

### Controller-View (рекомендація, не жорстка вимога)

Якщо компонент фічі виростає (стор/хуки + помітна верстка), корисно розділити його на контролер (читає стор, збирає props) і презентаційний View (верстка з props, без стору) — так простіше тестувати й читати. Для невеликих компонентів (мало розмітки, як `FieldList`, `PointList`) окремий View-файл не потрібен — усе лишається в одному компоненті.
Компоненти, що рендеряться всередині `MapContainer` (наприклад, `FieldsLayer`, `FieldFitController`), можуть напряму читати стор і використовувати `useMap()` — це їхня природна відповідальність, а не порушення шару.

### Правила коду (обов'язкові)

- TypeScript strict. **Заборонено `any`.** Для невідомих даних використовувати `unknown` і звуження типів. Приведення `as` лише з коментарем, чому воно безпечне.
- Тільки named exports (виняток: файли, де інструмент вимагає default, наприклад `vite.config.ts`).
- Імпорти між папками через alias `@/` (без `../../`). Усередині однієї фічі допустимі відносні `./`.
- Один React-компонент на файл, функціональні компоненти і хуки. Виняток: класовий `ErrorBoundary`, бо React не має хука для перехоплення помилок рендеру.
- Zustand: у сторі лише первинний стан і дії. Похідні значення обчислюються поза стором. Компоненти підписуються вузько (`useStore(s => s.x)`), ніколи на весь стор.
- Координати: у домені використовуємо `LatLng { lat, lng }`. GeoJSON зберігає `[lng, lat]`. **Конвертація порядку координат відбувається лише в `shared/lib/geo/geometry.ts`.** Більше ніде не пишемо `[lat, lng]` вручну.
- Ніколи `dangerouslySetInnerHTML`. Текст користувача виводимо лише як React-текст.
- Код і коментарі англійською, тексти інтерфейсу українською.
- Не вимикати правила ESLint коментарями. Єдиний виняток: точкове налаштування для згенерованих файлів shadcn (див. нижче).
- Код відформатований Prettier. Перед завершенням підпункту виконати `npm run pretty`.
- **Скоуп:** робити лише те, що описано в поточному підпункті. Не додавати бібліотеки, абстракції, функції «про запас».
- **KISS:** обирати найпростіше рішення, яке закриває вимогу ТЗ. Спершу локальний стан (`useState`) і звичайний код, стор і окремі файли/хуки лише тоді, коли стан реально спільний або код повторюється. Не ускладнювати код гіпотетичними сценаріями; відомі обмеження й припущення фіксувати в README. Якщо план підпункту здається складним, спершу запропонувати простіший варіант. Кожен рядок має бути легко пояснити на code review.

### shadcn/ui

- Компоненти додавати **лише через CLI** (`npx shadcn@latest add <name>`) і **лише тоді, коли вони потрібні в поточному підпункті**. Не додавати «набір на майбутнє».
- Згенеровані файли живуть у `src/shared/components/ui/`. Не переписувати їх без потреби, свої дублі примітивів (Button, Alert, Card тощо) не створювати. Після додавання виконати `npm run pretty`, щоб файли відповідали нашому стилю.
- Класи об'єднувати через `cn()` з `@/shared/lib/utils`.
- Якщо ESLint скаржиться на згенеровані файли (наприклад, `react-refresh/only-export-components`), вимкнути це правило точково для `src/shared/components/ui/**` у конфігу ESLint. Код згенерованих файлів не правити по суті.
- Тексти в компонентах українською, як і решта UI.

### Git

- Репозиторій уже ініціалізовано (гілка `main`). Віддалений репозиторій, `git remote`, пуш і створення гілок роблю я, агент цього не робить.
- **Коміти лише за критичним правилом на початку файлу.** Після мого дозволу агент комітить лише файли поточного підпункту і знову зупиняється.
- **Один підпункт плану = один коміт**, зміни різних підпунктів не змішуються, якщо я явно не попросив об'єднати їх в один коміт.
- Перед зупинкою в підпункті проходять `npm run typecheck`, `npm run lint`, `npm run pretty:check`, `npm run build`. `git status` показує лише файли цього підпункту. Тимчасові перевірки видалено, зайвих файлів немає.
- Кожен коміт має залишати проєкт у робочому стані, що збирається.
- README оновлюється в тому ж коміті, що й код підпункту, а не окремим комітом наприкінці.
- Повідомлення комітів у стилі conventional commits; агент пропонує його наприкінці підпункту.
- `.gitignore` покриває `node_modules`, `dist`, `*.local`, `.env*`, службові файли редакторів і ОС.
