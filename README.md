# Field Manager

Веб-застосунок для управління сільськогосподарськими полями: інтерактивна карта з полями (GeoJSON), моніторингові точки з координатами WGS84 і MGRS, панель зі списком полів і формою додавання точки. Тестове завдання на позицію Frontend Engineer. Без бекенду — лише mock-дані.

> Документ оновлюється разом із кодом. Поточний стан: карта з полями і моніторингові точки (додавання, іконки за типом, видалення). Список точок із фільтрами, пошуком і сортуванням та адаптив під планшет — у наступних кроках.

## Запуск

```bash
npm install
npm run dev
```

Інші команди:

```bash
npm run typecheck   # tsc -b
npm run lint        # eslint .
npm run pretty       # prettier --write .
npm run pretty:check # prettier --check .
npm run build        # tsc -b && vite build
```

## Використані технології

- **Vite** — build tool.
- **React** (остання мажорна версія шаблону `react-ts`) + **TypeScript strict**.
- **Leaflet** / **react-leaflet** (мажорна версія, сумісна за `peerDependencies` з установленим мажором React).
- **Tailwind CSS** для стилізації.
- **shadcn/ui** — компоненти (`Alert`, `Card`, `Button`, `Select`, `Textarea`, `Label`) генеруються CLI й живуть у репозиторії як власний код, не як залежність.
- **Zustand** — по стору на фічу.
- `mgrs` — конвертація WGS84 → MGRS на фронтенді.
- `@turf/boolean-point-in-polygon` — перевірка, що точка всередині вибраного поля.
- **ESLint + Prettier** (з плагіном для Tailwind).

## Архітектурні рішення

**Feature-based структура.** Код організовано за фічами (`src/features/map`, `src/features/fields`), кожна з підпапками `api/`, `components/`, `hooks/`, `stores/`, `types/`. Спільний код — у `src/shared`. Напрямок залежностей односторонній: `app → features → shared`; фіча імпортує іншу фічу лише через її `index.ts` (єдиний дозволений зв'язок у плані проєкту — `points → fields`, коли з'явиться фіча точок). Це командна домовленість, яка перевіряється на code review, а не ESLint-правилом (`no-restricted-imports` свідомо не використовували — це over-engineering для обсягу тестового завдання).

**Стор → контролер усередині карти, а не ref на інстанс карти.** Сайдбар зі списком полів рендериться поза `MapContainer`, тому не має прямого доступу до інстансу Leaflet-карти. Замість проброшування ref, список лише записує вибір у Zustand-стор; окремий компонент `FieldFitController`, який рендериться _всередині_ `MapContainer` і має доступ до `useMap()`, підписується на той самий стор і сам викликає `fitBounds`. Це тримає компоненти карти незалежними від того, хто саме змінив вибір (клік по карті чи по списку).

**Поля рендеряться через `<Polygon>`, а не `<GeoJSON>`.** Це дає прямий контроль над стилем активного/неактивного полігона через пропс `pathOptions`, без обхідних шляхів `<GeoJSON>` для динамічного рестайлінгу окремих feature.

**Конвертація порядку координат ізольована в одному модулі.** GeoJSON зберігає координати як `[lng, lat]`, домен застосунку використовує `{ lat, lng }`. Уся конвертація — в `shared/lib/geo/geometry.ts` (`latLngToLngLat`, `polygonToLatLngRings`); ніде більше в коді вручну не переставляються координати.

**Стор по фічах, вузькі підписки.** Кожна фіча має власний Zustand-стор (`fields.store.ts`); глобального стору немає. Компоненти підписуються на конкретні поля стору (`useStore(s => s.x)`), а не на весь стор, щоб зайві частини стану не викликали зайвих ререндерів. Похідні значення (наприклад, вибране поле за id) обчислюються поза стором, у хуку `useSelectedField`.

**Controller-View — рекомендація, не жорстка вимога.** Для невеликих компонентів (мало розмітки, як `FieldInfo`, `FieldList`) окремий View-файл не виносили. Компоненти, що рендеряться всередині `MapContainer` (`FieldsLayer`, `FieldFitController`), напряму читають стор і використовують `useMap()` — це їхня природна відповідальність, не порушення шарів.

**Фіча `points` залежить від `fields` лише через публічні хуки.** `points` отримує вибране поле, список полів і дію вибору через `useSelectedField`, `useFields`, `useSelectField` з `features/fields/index.ts`. Стор полів назовні не експортується.

**Додавання точки: чернетка → форма → точка.** Клік по невибраному полю зупиняється в `FieldPolygon` і лише вибирає поле. Клік по вибраному полю доходить до карти, де `AddPointController` перевіряє `isPointInPolygon` і записує в стор чернетку (`draft`). Форма в сайдбарі показується, лише якщо чернетка належить вибраному полю; це похідне значення, без `useEffect` для очищення. Підказки «Спочатку виберіть поле» / «Точку можна додати лише в межах вибраного поля» — це звичайний Leaflet-popup у місці кліку (тексти — наші константи, не ввід користувача).

**MGRS не зберігається.** Це похідне значення від WGS84, тому рахується під час рендеру (`toMgrs` у `shared/lib/geo/coordinates.ts`: `mgrs.forward` з точністю 1 м і пробілами для читабельності). Якщо конвертація неможлива (наприклад, біля полюсів), UI показує «Не вдалося обчислити», а решта працює.

**Точки зберігаються в `localStorage`** через `persist` із Zustand. Зберігаються лише `points`; чернетка — тимчасовий стан UI.

**Іконки точок — `L.divIcon` з кольоровим колом і літерою типу** (Г, Ш, Х, І). Leaflet малює маркери поза React, тому `divIcon` приймає HTML-рядок. У нього потрапляють лише наші константи (колір і літера), опис користувача показується тільки як React-текст у popup. Іконки створюються один раз на тип і спільні для всіх маркерів.

**`stopPropagation` у кнопці «Видалити» в popup.** Вміст popup react-leaflet рендерить через портал, а React слухає події на контейнері порталу, тобто ще всередині popup. `onClick` видаляє точку й popup раніше, ніж клік дійде до карти; відірвана від DOM кнопка вже не проходить перевірку Leaflet «клік усередині popup», і Leaflet сприйняв би його як клік по карті (ставлячи чернетку). Тому подію зупиняємо в обробнику.

**`parseFields` — простий мапер без рантайм-валідації (свідомо, KISS).** Mock-дані типізовані (`FeatureCollection<Polygon, FieldProperties>`) і перевіряються компілятором, тому перевірки в рантаймі для них були б мертвим кодом. Файл `fields.mock.ts` імітує відповідь сервера, а `parseFields` — межа, де з реальним API відповідь варто валідувати (див. «Що б я додав»).

**Межі карти рахує Leaflet.** `FieldFitController` передає всі точки полігонів у `L.latLngBounds`, замість власного підрахунку bounding box.

**Одиниця виміру площі.** У прикладі з ТЗ `"area": 45.2` не має вказаної одиниці виміру. Припущення: вважаємо гектарами. Для поля з ТЗ (`field-1`) це значення залишено без змін, хоча геометрично полігон займає ~78 га — розбіжність свідома, приклад із завдання вважаємо ілюстративним, а не таким, що має відповідати реальній площі полігона. Для решти полів площу порахували через `@turf/area` і округлили до 0.1.

**Припущення щодо точок.** Точка належить полю, в межах якого її створено (`fieldId`). Дані з `localStorage` не валідуються: ручне редагування сховища вважаємо поза межами завдання. Popup маркера відкривається і закривається повторним кліком по маркеру — це стандартна поведінка Leaflet.

**Фільтрація точок — чиста функція.** `filterPoints(points, filters)` у `features/points/lib/filterPoints.ts`: фільтр за типом → пошук у описі (без урахування регістру, з `trim`) → сортування за датою створення. Функція не залежить від React і стору та не мутує вхідний масив, тому її легко перевірити юніт-тестами. `createdAt` — рядки ISO 8601 в UTC одного формату, тож сортуються як звичайні рядки, без парсингу дат.

**Без роутингу, TanStack Query, `app/providers`.** Застосунок одноекранний і працює без бекенду (лише mock-дані), тому ці інструменти не додавали — вони б не несли функціональної цінності для цього обсягу завдання.

## Що б я додав, якби мав більше часу

- Іконки lucide на маркерах замість літер (через `renderToStaticMarkup`), щоб карта і список мали однакові іконки.
- Валідація зовнішніх даних на межах застосунку: відповіді API в `parseFields` (наприклад, через `zod`) і даних із `localStorage` під час відновлення стану, плюс версіонування/міграції формату.
- Редагування точок.
- Повноцінний адаптив під tablet (зараз лейаут фіксований, `sidebar` + `main`).
- `ErrorBoundary` навколо карти й списку для граційної деградації при неочікуваних помилках рендеру.
- Юніт-тести для чистої логіки (`parseFields`, `shared/lib/geo`, `filterPoints`) і, можливо, кілька інтеграційних тестів на вибір поля.
- Дебаунс для пошуку (`useDebounce`) і мемоізація важких обчислень у списку точок, якщо дані виростуть.
- Персистентність вибраного поля, щоб воно не губилося при перезавантаженні сторінки.
