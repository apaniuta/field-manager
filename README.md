# Field Manager

Веб-застосунок для управління сільськогосподарськими полями: інтерактивна карта з полями (GeoJSON), моніторингові точки з координатами WGS84 і MGRS, панель зі списком полів, формою додавання точки і списком точок із фільтром, пошуком і сортуванням. Тестове завдання на позицію Frontend Engineer. Без бекенду — лише mock-дані.

## Запуск

```bash
npm install
npm run dev
```

Інші команди:

```bash
npm run typecheck    # tsc -b
npm run lint         # eslint .
npm run pretty       # prettier --write .
npm run pretty:check # prettier --check .
npm run build        # tsc -b && vite build
npm run preview      # vite preview (перегляд зібраного dist)
```

## Використані технології

- **Vite** — build tool.
- **React 19** (остання мажорна версія шаблону `react-ts`) + **TypeScript strict**, без `any`.
- **Leaflet** / **react-leaflet 5** (мажорна версія, сумісна за `peerDependencies` з React 19). Тайли — OpenStreetMap.
- **Tailwind CSS 4** для стилізації.
- **shadcn/ui** — компоненти (`Alert`, `Card`, `Button`, `Select`, `Textarea`, `Label`, `Input`) генеруються CLI й живуть у репозиторії (`src/shared/components/ui`) як власний код, не як залежність. Іконки в UI — `lucide-react` (іде разом із shadcn).
- **Zustand** — по стору на фічу, `persist` для точок.
- `mgrs` — конвертація WGS84 → MGRS на фронтенді.
- `@turf/boolean-point-in-polygon` — перевірка, що точка всередині вибраного поля.
- **ESLint + Prettier** (з плагіном для Tailwind).

## Архітектурні рішення

**Feature-based структура.** Код організовано за фічами (`src/features/map`, `src/features/fields`, `src/features/points`); усередині фічі — лише потрібні їй підпапки (`api/`, `components/`, `hooks/`, `lib/`, `stores/`, `types/`). Спільний код — у `src/shared`, композиція фіч — у `src/app` (`App.tsx` збирає шари карти, `Sidebar.tsx` — панель). Напрямок залежностей односторонній: `app → features → shared`; фіча імпортує іншу фічу лише через її `index.ts` (єдиний дозволений зв'язок — `points → fields`). Це командна домовленість, яка перевіряється на code review, а не ESLint-правилом (`no-restricted-imports` свідомо не використовували — це over-engineering для обсягу тестового завдання).

**Стор → контролер усередині карти, а не ref на інстанс карти.** Сайдбар зі списком полів рендериться поза `MapContainer`, тому не має прямого доступу до інстансу Leaflet-карти. Замість прокидання ref список лише записує вибір у Zustand-стор; окремий компонент `FieldFitController`, який рендериться _всередині_ `MapContainer` і має доступ до `useMap()`, підписується на той самий стор і сам викликає `fitBounds` (без вибору — під усі поля). Це тримає компоненти карти незалежними від того, хто саме змінив вибір (клік по карті чи по списку). Так само працює фокус на точці: список пише `focusedPointId` у стор точок, а `PointFocusController` усередині карти робить `flyTo`.

**Межі карти рахує Leaflet.** `FieldFitController` передає всі точки полігонів у `L.latLngBounds`, замість власного підрахунку bounding box.

**Поля рендеряться через `<Polygon>`, а не `<GeoJSON>`.** Це дає прямий контроль над стилем активного/неактивного полігона через пропс `pathOptions`, без обхідних шляхів `<GeoJSON>` для динамічного рестайлінгу окремих feature.

**`memo` і `useMemo` у `FieldPolygon`.** Вибір поля ререндерить `FieldsLayer`, але оновитися мають лише два полігони, у яких змінився `isSelected`; `onSelect` — стабільна дія стору, тож `memo` відсікає решту. `useMemo` тримає стабільним масив сконвертованих координат: react-leaflet передає в Leaflet нові `positions` на кожне нове посилання на масив.

**Конвертація порядку координат ізольована в одному модулі.** GeoJSON (і turf) зберігає координати як `[lng, lat]`, Leaflet приймає `[lat, lng]`, домен застосунку використовує `{ lat, lng }`. Уся конвертація — в `shared/lib/geo/geometry.ts` (`latLngToLngLat`, `polygonToLatLngRings`, `isPointInPolygon`); ніде більше в коді вручну не переставляються координати.

**MGRS не зберігається.** Це похідне значення від WGS84, тому рахується під час рендеру (`toMgrs` у `shared/lib/geo/coordinates.ts`: `mgrs.forward` з точністю 1 м і пробілами для читабельності). Якщо конвертація неможлива (наприклад, біля полюсів), UI показує «Не вдалося обчислити», а решта працює.

**Стор по фічах, вузькі підписки.** Кожна фіча має власний Zustand-стор (`fields.store.ts`, `points.store.ts`); глобального стору немає. У сторі лише первинний стан і дії. Компоненти підписуються на конкретні поля стору (`useStore(s => s.x)`), а не на весь стор, щоб зайві частини стану не викликали зайвих ререндерів. Похідні значення (наприклад, вибране поле за id) обчислюються поза стором, у хуку `useSelectedField`.

**Controller-View — рекомендація, не жорстка вимога.** Головні компоненти фіч (`Fields`, `Points`) читають стор і передають дані й обробники через props презентаційним компонентам (`FieldList`, `PointForm`, `PointFilters`, `PointList`, `PointListItem`). Для невеликих компонентів окремий View-файл не виносили. Компоненти, що рендеряться всередині `MapContainer` (`FieldsLayer`, `FieldFitController`, `PointsLayer`, `PointFocusController`, `AddPointController`), напряму читають стор і використовують `useMap()` — це їхня природна відповідальність, не порушення шарів.

**Фіча `points` залежить від `fields` лише через публічні хуки.** `points` отримує вибране поле, список полів і дію вибору через `useSelectedField`, `useFields`, `useSelectField` з `features/fields/index.ts`. Стор полів назовні не експортується.

**`parseFields` — простий мапер без рантайм-валідації (свідомо, KISS).** Mock-дані типізовані (`FeatureCollection<Polygon, FieldProperties>`) і перевіряються компілятором, тому перевірки в рантаймі для них були б мертвим кодом. Файл `fields.mock.ts` імітує відповідь сервера, а `parseFields` — межа, де з реальним API відповідь варто валідувати (див. «Що б я додав»).

**Додавання точки: чернетка → форма → точка.** Клік по невибраному полю зупиняється в `FieldPolygon` і лише вибирає поле. Клік по вибраному полю доходить до карти, де `AddPointController` перевіряє `isPointInPolygon` і записує в стор чернетку (`draft`). Форма в сайдбарі показується, лише якщо чернетка належить вибраному полю; це похідне значення, без `useEffect` для очищення. Підказки «Спочатку виберіть поле» / «Точку можна додати лише в межах вибраного поля» — це звичайний Leaflet-popup у місці кліку (тексти — наші константи, не ввід користувача).

**Точки зберігаються в `localStorage`** через `persist` із Zustand. Зберігаються лише `points`; чернетка і фокус — тимчасовий стан UI.

**Іконки точок — `L.divIcon` з кольоровим колом і літерою типу** (Г, Ш, Х, І). Leaflet малює маркери поза React, тому `divIcon` приймає HTML-рядок. У нього потрапляють лише наші константи (колір і літера з `POINT_TYPE_META`), опис користувача показується тільки як React-текст у popup і списку — так XSS через опис неможливий. `dangerouslySetInnerHTML` у проєкті немає. Іконки створюються один раз на тип і спільні для всіх маркерів.

**`stopPropagation` у кнопці «Видалити» в popup.** Вміст popup react-leaflet рендерить через портал, а React слухає події на контейнері порталу, тобто ще всередині popup. `onClick` видаляє точку й popup раніше, ніж клік дійде до карти; відірвана від DOM кнопка вже не проходить перевірку Leaflet «клік усередині popup», і Leaflet сприйняв би його як клік по карті (ставлячи чернетку). Тому подію зупиняємо в обробнику.

**Фільтрація точок — чиста функція.** `filterPoints(points, filters, fieldId)` у `features/points/lib/filterPoints.ts`: обмеження полем (`null` — усі поля) → фільтр за типом → пошук в описі (без урахування регістру, з `trim`) → сортування за датою створення. Функція не залежить від React і стору та не мутує вхідний масив, тому її легко перевірити юніт-тестами. `createdAt` — рядки ISO 8601 в UTC одного формату, тож сортуються як звичайні рядки, без парсингу дат.

**Панель точок.** `Points.tsx` читає стор і тримає стан фільтрів у `useState`: вони потрібні лише списку, тому не потрапляють у стор і не зберігаються між перезавантаженнями. Під формою нової точки — `PointFilters` (пошук, тип, сортування, «Скинути») і `PointList` / `PointListItem`. У кожному рядку є назва поля, коло з кольором і літерою типу (ті самі константи, що й маркер на карті), опис, дата і кнопка видалення. У заголовку секції — лічильник «N з M». Окремі порожні стани: коли точок немає взагалі, коли у вибраному полі ще немає точок і коли фільтри нічого не знайшли. Кнопка «Скинути» з'являється в `PointFilters`, коли активний фільтр, тож порожній стан лише пояснює, без дубля кнопки. Сортування лише змінює порядок і не може сховати точки, тому не вважається активним фільтром (`hasActiveFilters`): зміна сортування в полі без точок показує «У цьому полі ще немає точок», а не «Нічого не знайдено».

**Вибране поле визначає межі списку.** ТЗ вимагає «список усіх доданих точок», а водночас цінує зручну навігацію між полями. Тому модель одна: поки поле не вибране, список показує точки всіх полів; після вибору поля — лише його точки. Окремого перемикача «лише вибране поле» немає (KISS): щоб повернутися до всіх точок, достатньо зняти вибір поля.

**Зняття вибору поля — повторним кліком по вибраному полю в списку.** Кнопки полів мають `aria-pressed`, тобто це перемикачі, і повторне натискання природно «віджимає» вибір (`selectField(null)`). `FieldFitController` при відсутності вибору сам підганяє карту під усі поля. Зняття вибору кліком по карті поза полями й Esc свідомо не додавали (див. «Що б я додав»).

**Без окремої картки «Інформація про поле».** Базову інформацію з ТЗ (назва, площа, а також культура) показує картка поля в списку, а вибрана картка підсвічена. Окрема картка з тими самими даними лише дублювала б її, а в порожньому стані займала місце підказкою «Оберіть поле».

**Клік по картці точки поводиться як клік по картці поля.** Він вибирає поле точки, центрує на ній карту (`flyTo`, зум не менше 16) і підсвічує картку тими самими стилями, що й вибране поле; повторний клік знімає фокус, як повторний клік по полю знімає вибір. Якщо видно точки всіх полів, після кліку список звужується до поля точки — це послідовно з тим, що вибране поле визначає межі списку. Зв'язок односторонній (список → карта): клік по маркеру лише відкриває popup. Деталі:

- `PointFocusController` рендериться після `FieldFitController`: ефекти сусідніх компонентів виконуються по порядку, тож `flyTo` до точки перекриває `fitBounds` її поля.
- Фокус скидається, коли сфокусована точка більше не належить вибраному полю (поле змінили в списку чи на карті або зняли вибір). Фіча `fields` про точки не знає, тому це робить `PointFocusController`, а не код вибору поля. Видалення сфокусованої точки теж скидає фокус.
- Однаковий вигляд вибраної картки поля і сфокусованої картки точки задає одна функція `selectableCardClassName` у `shared/lib/selection.ts`, а не два однакові рядки класів.
- У картці клікабельна частина — `<button aria-pressed>`, а «Видалити» — сусідня кнопка: кнопка всередині кнопки — невалідний HTML.

**Помилка завантаження тайлів.** `MapView` слухає `tileerror` / `tileload` і показує поверх карти `Alert` «Не вдається завантажити карту», поки тайли не почнуть вантажитися знову. Поля, точки й список при цьому працюють.

**Адаптив: desktop і tablet (вимога ТЗ).** Лейаут один для всіх ширин від 768 px: сайдбар фіксованої ширини `w-80` (320 px) ліворуч, карта займає решту. Окремих брейкпоінтів немає: 320 px вистачає і на планшеті в portrait, а на широкому екрані виграє карта, тож змінювати ширину сайдбару не було потреби.

Корінь займає `h-dvh` і має `overflow-hidden`, тож сторінка ніколи не прокручується — прокручується лише сайдбар. `w-screen` не використовуємо: `100vw` не враховує смугу прокрутки, а коли вміст сайдбару вищий за екран, відкриття Select могло прокрутити всю сторінку й сховати верх карти. `ResizeObserver` для карти не додавали: ширина сайдбару стала, розмір карти змінюється лише разом із вікном, а на `resize` вікна Leaflet сам перераховує розмір (перевірено в браузері на 1440×900, 1024×768, 768×1024 і при переході між ними).

Підказка з назвою поля на полігоні (`Tooltip sticky`) показується лише на пристроях з наведенням (`matchMedia("(hover: hover)")`). На тач-екрані Leaflet відкриває tooltip по тапу, і він лишається в точці тапу, тож накривав щойно поставлену точку. Назва поля й так є в списку, а вибране поле підсвічене. Медіазапит перевіряється один раз під час завантаження: після перемикання емуляції пристрою в DevTools сторінку треба перезавантажити.

На тач-екранах (`@media (pointer: coarse)`) кнопки, поля вводу, Select і пункти його списку мають висоту щонайменше 40 px, а кнопки-іконки ще й ширину 40 px: стандартні 28–32 px shadcn замалі для пальця. Це одне правило в `app/index.css` за атрибутом `data-slot`, який shadcn ставить на кожен компонент. Так не довелося ні правити згенеровані файли, ні додавати класи в кожному місці використання. Desktop зберігає компактні розміри.

Ієрархія сайдбару: заголовок застосунку, розділені лінією секції «Поля» і «Точки»; форма нової точки — окрема картка.

**Без роутингу, TanStack Query, `app/providers`.** Застосунок одноекранний і працює без бекенду (лише mock-дані), тому ці інструменти не додавали — вони б не несли функціональної цінності для цього обсягу завдання.

## Припущення

- **Одиниця виміру площі.** У прикладі з ТЗ `"area": 45.2` не має вказаної одиниці виміру. Вважаємо гектарами. Для поля з ТЗ (`field-1`) значення залишено без змін, хоча геометрично полігон займає ~78 га — приклад із завдання вважаємо ілюстративним. Для решти полів площу порахували через `@turf/area` і округлили до 0.1.
- **Точка належить полю**, в межах якого її створено (`fieldId`).
- **Дані з `localStorage` не валідуються:** ручне редагування сховища вважаємо поза межами завдання.
- **Фільтри впливають лише на список.** Карта завжди показує всі точки, щоб пошук у списку не ховав дані з карти.
- **Popup маркера** відкривається і закривається повторним кліком по маркеру — стандартна поведінка Leaflet.
- **Вибране поле не зберігається** між перезавантаженнями, на відміну від точок.
- **Телефонний лейаут (< 768 px) свідомо не робили** — у ТЗ є лише desktop і tablet.

## Що б я додав, якби мав більше часу

- Іконки lucide на маркерах замість літер (через `renderToStaticMarkup`), щоб карта і список мали однакові іконки.
- Валідація зовнішніх даних на межах застосунку: відповіді API в `parseFields` (наприклад, через `zod`) і даних із `localStorage` під час відновлення стану, плюс версіонування/міграції формату.
- Редагування точок.
- Дебаунс для пошуку (`useDebounce`): зараз фільтрація синхронна на кожен символ, для десятків точок цього досить.
- Юніт-тести для чистої логіки (`parseFields`, `shared/lib/geo`, `filterPoints`) і, можливо, кілька інтеграційних тестів на вибір поля.
- `ErrorBoundary` навколо карти й списку для граційної деградації при неочікуваних помилках рендеру.
- Кластеризація маркерів, коли точок стане сотні.
- Персистентність вибраного поля, щоб воно не губилося при перезавантаженні сторінки.
- Лейаут для телефона (< 768 px, поза ТЗ): колонка — карта зверху (~50vh), панель знизу; той самий варіант — для портретного планшета.
- Сайдбар, що згортається: у портретному режимі планшета (768 px) карта займає лише 448 px, а кнопка «сховати панель» віддала б їй весь екран.
- Плашка вибраного поля на карті (справа вгорі: назва + «×» для зняття вибору). Зараз вибір знімається лише повторним кліком у списку; плашка стане потрібною разом зі згортанням сайдбару, бо без нього не видно, яке поле вибране.
- Більші кнопки масштабу карти на тач-екранах (це контроли Leaflet, а не shadcn, тож правило з `index.css` їх не зачіпає).
- Віртуальна клавіатура на планшеті: під час введення опису точки прокручувати поле й кнопку «Зберегти» у видиму частину екрана.
- Синхронізація фокусу точки в обидва боки: клік по маркеру підсвічує картку в списку, а фокус із картки відкриває popup маркера (після завершення `flyTo`, на `moveend`, щоб auto-pan popup не конфліктував з анімацією), закриття popup знімає фокус. Свідомо спростили до односторонньої дії: це ~75 рядків нетривіальної синхронізації (ref на маркер, ефект, `popupclose`) поза вимогами ТЗ.
- Зняття вибору поля кліком по карті поза полями. Свідомо не робили: повторного кліку в списку достатньо. Для цього, як і для відомої дрібниці «клік усередині поля, що закриває popup маркера, одразу ставить чернетку точки», треба ігнорувати клік, який лише закриває popup (Leaflet закриває його ще до `click` карти): на `mousedown` запам'ятати, чи був відкритий popup.

## Нотатки для презентації (30 хв)

**Демо (~10 хв).** Старт: карта підігнана під усі поля → вибір поля в списку і на карті (підсвітка, `fitBounds`) → клік поза полем і поза вибраним полем (підказки) → клік усередині: чернетка, форма з WGS84/MGRS → збереження, маркер із літерою типу, popup, видалення → список точок: пошук, тип, сортування, «Скинути», лічильник «N з M», порожні стани → клік по картці точки (`flyTo`, звуження списку, повторний клік) → зняття вибору поля → перезавантаження (точки збереглися) → вимкнена мережа (Alert про тайли) → tablet у DevTools.

**Огляд коду (~10 хв).** `app/App.tsx` (композиція шарів) → структура `features/*` та їхні `index.ts` → `fields.store.ts` / `points.store.ts` (лише первинний стан) → `useSelectedField` (похідне значення) → `FieldFitController` / `PointFocusController` → `shared/lib/geo/geometry.ts` і `coordinates.ts` → `filterPoints.ts`.

**Обґрунтування (~10 хв), питання, до яких варто бути готовим:**

- чому `parseFields` без рантайм-валідації (mock типізований; валідація на межі API — у «Що б я додав»);
- чому `stopPropagation` у кнопці «Видалити» в popup (React-портал vs перевірка кліків Leaflet);
- `memo` / `useMemo` у `FieldPolygon`;
- стор → контролер усередині карти замість ref на карту;
- конвертація координат лише в `geometry.ts`; MGRS як похідне значення;
- `divIcon` з константами замість тексту користувача (XSS);
- чому фільтри в `useState`, а не в сторі; чому сортування не «активний фільтр»;
- чому без роутера, TanStack Query і лінтер-правил для меж фіч.
